## 0. Why

The first pilot (2026-10-03) proved the trust chain and the attempt protocol end to end and stopped at the accept step on missing mechanisms, not on bugs in the mechanisms that exist. Every hand-off between members needed a human message, the worker had no official way to know which repository to clone and with which credential, the coordinator could not record its own triage, and the operator could not read the admin commands without an explanation. The product goal is a team that works without babysitting, onboarded by a handful of readable commands. This proposal turns the pilot's findings into design decisions.

## 1. Principles

1. **One owner per fact.** The aimem hub owns projects and everything that is a property of a project: its data, its process pin, its repository, and the access of teams to it. aicrewd owns teams, their names, members, attempts and the members' capabilities. A fact is declared once, where its owner lives, and read by the other side.
2. **A member learns everything from its home and its inbox.** No instruction that matters arrives by chat: the team's hub, projects, repositories and credential requirements are in the home; the task, repository and base of an attempt are in the offer.
3. **Credentials are per member and per purpose, and each is delivered by its issuer.** Every member has its own identity on the hub and on each forge host the team's projects use; material lives only in the member's home under `creds/` and in its aimem installation; declarations never carry values. The aimem credential is delivered by aimem (3.9); forge credentials are delivered through aicrewd only as deposits with the custody rules of 3.8. A credential is referenced by forge host, account and purpose (WORKSPACE), never by kind alone. What a token can do is decided by the forge; declarations state what is required so it can be checked before work, not at `git push`.
4. **Commands read as sentences.** Entity names are named flags; where an entity has an ID and a name, two explicit flags; names accepted wherever IDs are; one `--` style in both tools; one flag name for each recurring intent and secret kind (6.4).
5. **No workaround ships as a procedure.** What the pilot did by hand (hand-copied tokens, typed start prompts, manual READY) is replaced by software or by an operator step that exists for a reason.
6. **No silent refusal.** Whatever is refused for a missing right or capability is refused by name, to the party that can act on it, with the command that fixes it.
7. **Capabilities never authorize.** A capability reported by a member (3.6) or read from the hub by aicrewd (2.3) is a planning fact that makes refusals early; the authority to act stays with the party that enforces it (the forge for tokens, the hub for grants, aimem for task writes). No reported capability grants anything.

## 2. Projects, repositories, teams

**2.1 A project has one repository, declared on the project in aimem.** `aimem project repo set --project <p> --kind github|gitea|gitlab --url <clone url> [--access read|write]` and `project repo clear`; `aimem project show --project <p>` prints repository, process pin and grants. `--access` defaults to `write` (branches and pull requests); `read` is for projects members only consult. `--kind` is the API dialect used to verify a credential against that forge; the credential a member needs is identified by the host of the clone URL (`github.com`, `gitea.example.org`), so two projects on two instances of one forge need two credentials. The property carries no default branch: the forge owns it, and the coordinator reads it at offer time (3.5). The process repository stays a separate project property (`process select`, as today); its host adds a read requirement. Cross-repository work is tasks in each project with dependencies between them, as the AIForge work was run so far. Task 01a102f8-bb79 (aimem side).

**2.2 Team creation declares no projects; aicrewd owns the team's name.** `aicrew team create --name <team> --hub <alias>` creates the team in aicrewd and registers it on that hub through the peer operation `team.register` (2.3). The hub alias is one aicrewd knows from its configuration (an `aimem` block per hub, named; an implementation change in the 2.2-to-3 increment). The team name has one writer, aicrewd: the hub profile mirrors it, the hub offers no operator rename of a team profile, and `aicrew team rename` re-registers. Names are unique per peer; `team.register` refuses a name another team of the same peer holds (`team_name_taken`). Grants bind the profile's UUID, so a rename moves no grant; `aimem identity team grant` and `revoke` resolve `--team-name` within the peer and print the UUID they acted on, so the operator sees which profile received the project. Task 01a102f8-bb84 (aicrew) and the register operation in 01a102f8-bb79 (aimem).

**2.3 Project access is the hub's grant, read by aicrewd through two bounded peer operations.** `aimem identity team grant --peer <service> --team-name <team> --project <project>` is the only place a project is attached to a team; `revoke` detaches it; both stay hub-admin operations, never a peer's. aicrewd keeps no project or repository list of its own: the set of projects a team works on is the set of its grants, read from the hub. The two operations, each permitted to a peer credential issued for exactly that operation (identity.v1 rule since C6b):

- **`team.register`** (input: aicrew team UUID, name). Creates the profile for that UUID under the calling peer, or renames it. It acts only on profiles of the calling peer, never creates or touches a grant, never re-enables a profile the operator disabled, and never changes anything else on the profile. Refusals, each by name: `peer_forbidden` (credential not issued for this operation, or the UUID belongs to another peer), `team_name_taken` (another team of this peer holds the name), `profile_disabled` (the operator disabled this profile; the operator re-enables, aicrewd does not), `invalid_request` (malformed UUID or name; identity.v1's existing code). Audit: peer, UUID, old and new name, outcome.
- **`team.read`** (input: aicrew team UUID, or none for all teams of the peer). Returns, for the calling peer's own teams only: the profile's UUID, name and enabled state, the granted projects, and for each granted project its repository (kind, url, access), its process pin and nothing else: no tasks, no members, no knowledge, no other peer's teams. A disabled profile is returned with `enabled: false` and no grants; an unknown UUID answers `not_found`; a credential not issued for this operation answers `peer_forbidden`. Audit: peer, UUID, outcome.

aicrewd calls `team.read` at offer time, at `team show`, at `team check` and in the reconciliation loop, caches the result for its planning facts (3.6, 3.7) and refuses an offer on a project the team is not granted with a readable code (`project_not_granted`). The hub answer at offer time is authoritative for the grant and the repository; the cache serves only `show` and the gap announcements. The process pin an offer carries is not taken from `team.read`: COORDINATION-WIRE keeps it from aicrewd's own record of the step, and aimem rechecks it at commit; the pin `team.read` returns serves `show`, `check` and the gap announcements only. The inbox visibility rule of CREW-CONTRACT (messages scoped to the team's project set) keeps its meaning with the grants as the project set, read through `team.read`. `-project` disappears from `aicrew team create`.

**2.4 `aicrew team show` and `aicrew team check` are the health check of the whole setup.** `team show --team-name <team>` prints the team whole: hub, registration state on the hub, granted projects with their repositories, process pins and access levels (read from the hub), members with roles, session state and verified capabilities per forge host. `team check --team-name <team>` walks the chain and reports each link green or red with the fixing command: hub reachable, peer registered and `peer check` passing, team registered and enabled, every grant's repository and process pin resolvable, every member's capabilities against the requirements, pending deposits (3.8). `aicrew doctor` does the same for the service itself (configuration, token files, the deposit key, TLS, the aimem blocks, `/healthz`).

## 3. Credentials, identities, capabilities

**3.1 Every member has its own forge identity and token, per forge host.** The operator creates it on the forge (GitHub: an account or App per member; Gitea and GitLab: a bot user) and issues the token with the rights the granted projects' repositories on that host need. aicrewd holds no forge authority and mints nothing (a broker through a GitHub App is out of scope and would be its own proposal). One account per member per forge host is the scope of this proposal; a second account on the same host is out of scope (8).

**3.2 `join` provisions every credential the team's granted projects require, keyed by forge host.** The aimem credential arrives through aimem's own enrollment (3.9). Forge material arrives either as deposits under the invitation (3.8, the normal path) or as files on the command line (`--cred <host>=<file|->`, owner-only or `-` for standard input, the fallback for a machine the operator provisions by hand). For each host, `join` verifies the token with a read-only "who am I" call to that forge, then writes it to `<home>/creds/<host>.<account>.<purpose>` following WORKSPACE's credential reference (`github.com.example-bot.repo-write`), where `<account>` is the identity the forge reported and `<purpose>` is `repo-write` or `repo-read` from the highest access any granted project on that host requires. Before provisioning anything, `join` fetches the team's requirements from aicrewd and prints them against what it has ("team aiforge requires github.com (write), gitea.example.org (read); available: github.com; missing: gitea.example.org"); a missing host is a warning in the report and in `agent.json`, not a stop. `agent.json` lists, per host, the account and purpose and the file, never a value. A host unreachable at `join` leaves that credential unprovisioned with its message; it is not written under a guessed name. Task 01a102e1-354c.

**3.3 `check` verifies each credential against the declarations** by the same "who am I" call and, per granted project on that host, a read of its repository and, for `write`, the token's push and pull-request rights as the forge reports them. It prints a table: project, repository, host, account, required access, verified or missing. Only the member's machine can verify a token, since only it holds the value; aicrewd learns the result through the member's authenticated session (3.6). A home missing a forge credential is not blocked by that alone (see 3.6); a home missing the aimem credential is.

**3.4 Use is confined.** Clones made from the offer's repository get a per-clone credential helper that selects the member's file by the clone URL's host and reads it, and the member's commit identity derived from its account on that host. The value never appears in a URL, a global git configuration, process arguments, logs or chat.

**3.5 The offer names the repository and its base; the coordinator resolves the base.** Offer and independent claim carry `repository: {kind, url, access, default_branch, base_commit, branch}`. Kind, url and access come from the hub's project property (2.3); the coordinator's agent resolves `default_branch` and `base_commit` at offer time by a read of the forge with the coordinator's own credential for that host (so the coordinator role requires a read capability on every granted repository's host, 3.6), and names `branch` by the existing attempt-branch rule of CREW-CONTRACT; an independent claim resolves them the same way with the claimer's credential. All six fields are recorded on the attempt at creation and never change for its lifetime (11). The coordinator chooses the task and the worker, not the repository. Task 01a102e1-354c.

**3.6 Capabilities make refusals early.** At `join`, `check` and session start the agent reports its verified capabilities (per forge host: account, access level, the repositories verified) to aicrewd, which stores them per member as planning facts (principle 7). The coordinator's `/crew-offer` shows which workers can take a task of that project; aicrewd refuses an offer to a worker that lacks the required capability, with a readable code naming the missing host and access (`capability_missing`), before it reaches the inbox; the worker's own check is the last guard at accept. A missing capability never blocks the home or the member's other work. Task 01a102e1-354c.

**3.7 A changed requirement is announced, not discovered.** When a project is granted to a team or a project's repository changes, aicrewd notices in its reconciliation loop (it rereads `team.read` with the same cadence it reconciles steps) and, for every member whose capabilities fall short, puts a message in that member's inbox naming the project, the missing host and access and the command (`aicrew-agent join --home <home> --cred <host>=<file>`, or the deposit the operator should make), shows the gap in `aicrew team show`, and answers `aicrew team check` with the full list of gaps so the operator sees right after a grant who needs which token. Until the member adds the material, only offers that need it are refused, each by name. Task 01a102e1-354c.

**3.8 Forge deposits: a forge credential travels with the invitation, once, after the member is proven.** The operator attaches the member's forge credentials to the invitation instead of moving files between machines: `--deposit <host>=<file>` on `aicrew invitation issue` (3.9 shows the whole command). Only forge credentials can be deposited; the aimem credential never is (3.9). Custody and delivery:

- **At rest.** aicrewd stores each deposit encrypted with a key held by the service account outside the store directory, named in `aicrewd.json` (`deposit_key_file`), bound to the invitation and expiring with it. A dump of the store without the key yields nothing; the key file is owner-only and never leaves the host.
- **Delivery after proof.** The deposits are released only in the step after redemption has completed, that is after aicrewd has the aimem receipt that proves the member's hub identity (ONBOARDING-CONTRACT independent proof), over the same authenticated TLS session, to the agent whose identity the receipt established. The aicrew invitation subcode alone (without the enrollment subcode of the same envelope) therefore obtains no deposit: completion needs an aimem credential it does not carry.
- **Acknowledged delivery.** `join` writes the material into the home, then acknowledges; aicrewd deletes the deposit on the acknowledgment, not on sending. A lost response is retried: until the acknowledgment the deposit stays and `join --home <home>` (the existing completion retry) delivers it again to the same identity. Partial delivery is therefore distinguishable from success: a deposit still present means the member has not confirmed it, and `team check` lists it under pending deposits.
- **Audit and listing.** Every issue, delivery, acknowledgment, expiry and revocation is audited with invitation, agent, host, time and outcome; `aicrew invitation show` lists deposits by host and state, never a value.
- **Attacker outcomes.** Invitation subcode alone: nothing. Whole envelope stolen before the member uses it: see 3.9, the one-time code's own exposure. Compromised aicrewd host with the key: the forge deposits pending at that moment, never a member's aimem bearer and never a delivered deposit (deleted). Compromised member session: its own home's material, as today.

An expired or revoked invitation takes its deposits with it. aicrewd holds a member's forge secret only between `invitation issue` and the acknowledgment of `join`; long-term storage stays in the member's home. Later additions (a new host after a grant) use a deposit on a `link` invitation for that agent, redeemed by `join --home <home>`. Task 01a102e1-354c.

**3.9 The aimem credential is delivered by aimem (D1 enrollment); the member receives one one-time code.** This follows aimem's approved DESIGN-AIFORGE-ENROLLMENT (D1) and changes it in one named place (the operator-side file, below).

- **Issuance, on the operator's machine.** The operator issues the aimem enrollment subcode under aimem operator authority: `aimem identity enroll issue --purpose new-user --hub <hub id> --expires 24h --output <subcode file>` (D1: at least 128 bits, stored by digest, single use, 24 h by default and never more than 72 h; the file also carries the non-secret bundle ID and the hub's locator and identity binding). Then the console client issues the aicrew invitation and composes the envelope: `aicrew invitation issue --team-name <team> --role <role> --expires 24h --bundle <subcode file> --deposit github.com=<file> --output <envelope file>`. The console client sends aicrewd the invitation request with the bundle ID and the deposits, never the enrollment subcode; aicrewd answers with the invitation subcode; the client composes the envelope locally (both subcodes, bundle ID, hub and service locators with their identity bindings, version and checksum) and writes it to the owner-only `--output` file. If aicrewd refuses, nothing is revealed and the client prints the command that revokes the aimem subcode (`aimem identity enroll revoke --bundle <id>`); the operator retries with a new bundle. **The one D1 change:** D1 lets the operator see the subcodes only while composing; here the composed envelope is written to an owner-only file on the operator's machine, for the private hand-off, and the operator deletes it after sending. It never goes into ordinary configuration, Git, logs, tasks or chat, and `join` never reads it from a file.
- **New member: `new_user`.** The hub user does not exist before the envelope is redeemed: aimem creates the stable user and its installation credential in the redemption transaction, with no grants of its own; the aicrew invitation carries no `--expect-user` pin, the proof receipt names the created user, and the client compares the verified hub and user and the invitation's team and role to the envelope's scope before accepting success (D1). A member that already has a working credential never needs an envelope: `join --home <home>` resumes with the credential it has. An existing identity on a clean machine is D1's privileged reissue, an operator recovery under D1's own runbook, not part of the routine onboarding here.
- **Redemption, on the member's machine.** `aicrew-agent join --label <l> --client claude` reads the envelope at a hidden prompt, keeps both subcodes in process memory only, validates format and expiry, and verifies the hub and aicrewd against the envelope's identity bindings before sending anything (no trust on first use; `--url` and `--hub` are not needed when the envelope supplies them). Then, in D1's order: it redeems the enrollment subcode directly at the hub and stores the bearer in the home's aimem installation; it verifies the resulting identity with the hub and discards the subcode; it runs the aicrew invitation flow (begin, proof with its own bearer, complete); it receives the forge deposits (3.8) and acknowledges them. Nothing of the envelope touches the member's disk.
- **Stolen envelope.** The envelope is a one-time code with the exposure of every one-time onboarding code, which is why it travels privately and expires fast. Whoever redeems it first becomes the member: a new hub user with no grants beyond what the team's profile later gives, the team membership, and the forge deposits. The legitimate member's `join` then fails (`enrollment_invalid` from the hub, or the consumed invitation from aicrewd), and that failure is the operator's signal. Mitigations: single use, so there is never a second member from one envelope; expiry of 24 h by default and 72 h at most; no deposit beyond forge tokens, which the operator revokes on the forge. Operator response: disable the created hub user and revoke its credential (the aimem audit names the bundle), revoke the membership in aicrewd, revoke the deposited forge tokens on their forges, issue a new envelope.
- `--aimem-token-file <file|->` stays as the fallback for a bearer the operator issued by hand on an installation it provisions itself.

Task 01a102e1-354c (aicrew); the operator-side file is the one D1 change (10).

## 4. Members act without a human message

**4.1 Wake-up.** The launcher, which already holds the inbox, wakes the client when a message arrives; a member never ends a turn waiting. Task 01a0d6d7-1aed (raised to prerequisite).

**4.2 Initial instruction.** `run` hands the client a managed first instruction (`/crew-start`) so the first turn reads the home guidance and the inbox without a typed message; `run -- <client args>` still passes extra arguments; an operator flag disables it for debugging. Task 01a102cc-3a60.

**4.3 Managed slash commands.** `join` writes the role's commands into the home, namespaced `crew-` and checked against the client's built-ins and the user's own skills: `/crew-start`, `/crew-inbox`, `/crew-offer`, `/crew-triage` (coordinator only, 5), `/crew-review`, `/crew-accept`, `/crew-submit`, `/crew-handoff`; generated from the same source as ROLES.md. Task 01a102d2-ef73.

**4.4 The home names its team's projects and hub.** Written by `join` from the hub's grants and aicrewd's team record; shown in START.md and by `session status`. Task 01a102cc-3a4b.

**4.5 Session rule.** Under `run` the launcher holds the session; `session start`, `session leave` and `run` refuse to execute from inside a launched client (the launcher's environment variables are present) and name `aicrew-agent inbox` as the next action; START.md step 5 says so. Task 01a102d0-0d7b.

## 5. Coordinator triage in team mode: decision (a), bounded

A coordinated claim requires the task READY; today a team session has no task write, so the pilot's coordinator could not record its own triage (PILOT-RUN-1, P7). Two options were compared; the operator chose **(a)** on 2026-10-04.

**5.1 The decision.** The coordinator role gets task triage authority in team mode through the team profile: state BACKLOG and READY in both directions, priority, size, `next_action`, and comments, on tasks of the projects the profile is granted. Bounds:

- **Held tasks are untouchable.** A task under a reservation (any member's, the coordinator's own included) refuses every triage write with `task_held`; the existing rule that generic writes are refused while held stays. Triage happens before a claim or after a release, never under a hold.
- **Authority is the grant.** The write is allowed only on tasks of projects granted to the team profile, and only when aicrewd's team-mode context names the member's role as coordinator (introspection already returns the role); a worker's team session keeps `task_write: false`. The role is a fact aicrewd asserts about its own team; the hub trusts the peer for it, as it already does for the coordination facts.
- **Actor is the member.** aimem records the coordinator's user ID as the actor, as for every team write; the task history shows who triaged.
- **Partial update.** The aimem increment adds a partial task update (or a dedicated state transition) so a triage write never replaces the field set: the pilot's `update_task` cleared `epic` and `candidate_refs` (P7).
- **Readable refusal.** A coordinated claim on a not-READY task answers `task_not_ready` (status 409, `retryable: no`, since the refused claim's coordination proof and key are spent as for every coordination refusal; next action: the coordinator triages to READY and begins the step again through aicrew with a new offer) instead of `reservation_conflict`.

Task 01a102d9-440b (aicrew: the role in the context aicrewd reports, `/crew-triage`), and an aimem task filed from this revision (the profile capability, `task_held`, `task_not_ready`, the partial update).

**5.2 Why (a), and what it costs.** The comparison the decision rests on:

| | (a) coordinator writes triage through the team profile | (b) the offer carries the READY assessment |
|---|---|---|
| Who may change task state in team mode | the coordinator, on unheld tasks of granted projects | nobody directly; aimem moves one task to READY as part of a claim it verifies against the aicrew offer |
| Proof required | the team session plus aicrewd's role assertion in the team-mode context | an aicrew-verified offer or independent claim naming that task; the assessment is bound to the fact, never taken from the claimer's body |
| Actor recorded | the coordinator's user ID | the coordinator from the verified fact, as for the claim |
| Held tasks | refused (`task_held`) | not reachable (a held task is already claimed) |
| What a compromised coordinator session can do | triage any unheld task of the granted projects: state between BACKLOG and READY, priority, size, next action, comments; no content edits beyond those fields, no held task, no other project | make READY exactly the task its own offer names, inside a fenced claim; nothing else |
| What a compromised aicrewd can do | assert the coordinator role for any of its own linked members and so enable triage writes on the granted projects, attributed to that real member and made through that member's own session; it holds no member bearer, so it writes nothing itself (the context contract's existing trust in the peer's role assertion) | assert an offer for any task of a granted project, which a member's claim then turns into READY and a hold; the same trust in the peer's facts |
| What it covers | all of triage: grooming, splitting, priority, returning to BACKLOG, before any offer exists | only "ready for this attempt"; the rest of triage keeps no path in team mode |
| Contract cost | context matrix coordinator row, team-mode report `task_write`, reservation.v1 `task_held`/`task_not_ready`, task API partial update | coordination.v1 amendment or new version after C5-w3 was declared the last in-place amendment, plus reservation.v1 `task_not_ready` |
| Board | shows triage as it happens; the board stays authoritative | shows BACKLOG until a claim lands |

(b) has the smaller reach for a compromised session. (a) was chosen because the pilot needed the whole of triage, not one transition, because the board must show the decision before an offer exists, and because (a) stays inside the existing authority model (grant plus role) while (b) couples aimem's coordination contract to aicrew's attempt semantics. The reach of (a) is bounded by the grant, the hold rule and the field list above, and recorded per actor.

## 6. Readable commands

**6.1 aimem admin commands** (`aimem identity …`, `aimem access …`, `aimem project …`): entity names are named flags (`--peer`, `--team-name`/`--team-id`, `--project`, `--user-name`/`--user-id`, `--group-name`/`--group-id`, `--operation`); a positional argument only where a command has exactly one entity (`aimem identity peer check <service>` stays); the old positional form kept one release with a notice; team profiles carry `team_name`; output prints names beside IDs; `--help` shows a full example. Vocabulary rules: `--project` is the long form everywhere and `-p`, which every project-taking command uses today, stays as its alias; `aimem project <verb>` is the namespace of the new commands (`repo set`, `repo clear`, `show`) while the existing `projects`, `project-id` and `drop-project` stay as they are, with their `aimem project …` forms added as aliases in the same release; `access grant` subjects that may be a group take `--group-name`/`--group-id` with the same exclusive rule as users. The selector rule (exactly one of name or ID) applies to looking up an existing entity; a command that creates an entity whose ID the hub generates takes only the name (`access user-add`, `group-add`), and a command that renames one takes the ID plus the new name (`access user-set`, and any future rename). Task 01a102f8-bb79.

**6.2 aicrew commands** accept names wherever IDs are accepted (`--team-name pilot`), print both, and the documentation uses `--` for both tools.

**6.3 Names.** `service_id` names the deployment's service: `aicrew-service` for this deployment (renamed before the resume). `aicrew introspection-credential` becomes `aicrew hub-credential` (the credential this service issues to a hub), old name kept one release. Task 01a102ee-a2cd.

**6.4 One flag per intent and per secret kind, in both tools.** Writing a secret to a new owner-only file is always `--output <file>` (today `-code-file`, `-secret-file`, `-file` in aicrew and `--secret-file` in aimem, and standard output in `aimem access token-issue`); the file must not exist, is created readable by its owner only, and the value never goes to the terminal. Reading a secret: each kind a command reads has one flag named for that kind, the same in every command that reads it, and `-` reads standard input everywhere (a hidden prompt when standard input is a terminal is a nicety, not a requirement). The kinds and their flags: the tool's own credential, `--token-file` in aicrew (the operator token, as today) and `--admin-token-file` in aimem (the admin token, as today); a forge credential for a home, `--cred <host>=<file|->`; a forge credential attached to an invitation, `--deposit <host>=<file>`; an aimem bearer issued by hand, `--aimem-token-file <file|->`; the enrollment subcode file, `--bundle <file>`. The onboarding envelope is never a flag: `join` takes it at a hidden prompt only (3.9). Old names kept one release with a notice. Covered by 01a102f8-bb79 (aimem) and 01a102ee-a2cd extended to the aicrew client (aicrew).

## 7. Target onboarding, once this ships

Once per project (owner of the data): `aimem project repo set --project <p> --kind github --url <url>` and `aimem process select … --project <p>`. Once per team: `aicrew team create --name <team> --hub <alias>`; `aimem identity team grant --peer <service> --team-name <team> --project <p>` per project (prints the UUID granted); `aicrew team check --team-name <team>` (for this deployment: a team `aiforge` granted `aicrew`, `aimem` and `aiskills`, all on `github.com`, so one GitHub token per member covers them). Per member: a forge identity and token on each host the team needs; `aimem identity enroll issue --purpose new-user --hub <hub id> --expires 24h --output <subcode file>`; `aicrew invitation issue --team-name <team> --role <role> --expires 24h --bundle <subcode file> --deposit github.com=<token file> --output <envelope file>`; the envelope goes to the member privately, the operator deletes the file, nothing else travels. Member, once: `aicrew-agent join --label <l> --client claude`, the envelope at the hidden prompt; `join` enrolls at the hub (the hub user is created there), redeems and completes at aicrewd, receives the forge deposits, provisions the home and ends `ready` with the capability table per host. Work: `aicrew-agent run --client claude --home <home>`; the client starts with `/crew-start`; the human merges pull requests and watches `aicrew team show`. What a machine then needs before the envelope: the installed binaries (aimem, aicrew-agent, the client) and an active account with the model provider for the client; everything else arrives at join.

## 8. Out of scope

Token minting or brokering by aicrewd; a shared project token; several repositories per project and multi-repository offers; a second account on the same forge host for one member; several teams per home; OpenCode carriers and commands (1af8); event-driven delivery beyond the launcher's wake-up; a web console (a future client of the operator API); deleting hub profiles when a team is removed; depositing the aimem credential through aicrewd (3.9 replaces it); D1's existing-identity reissue (an operator recovery under D1's runbook, not routine onboarding).

Later, its own proposal: toolchain requirements (forge CLIs such as gh or tea, LSP servers, MCP servers, skills) declared at the organization level (the process manifest in aiskills, which is the company's development process), at the project level (language, forge), at the role level (coordinator and worker), and verified against the host by `check` with verified installers, as aimem and ai-skills are today. Also later: delivering the model provider's credential to the client from the home.

## 11. Failure modes of the new mechanisms

| Situation | Outcome | Recovery |
|---|---|---|
| Hub unreachable, or `team.read` refused, at offer time | the offer is refused (`hub_unavailable` or the refusal's own code); nothing is sent to the worker; aicrewd never falls back to its cache for an offer | retry when the hub answers; `team check` shows the link red |
| Grant revoked while an attempt is running | aimem denies the next affected team operation (context contract lifecycle); the reservation is not released silently; aicrewd notices in reconciliation, sets the attempt `blocked` (reason: grant revoked) and tells coordinator and worker | the operator re-grants, or closes the attempt under the coordination contract's closure rules; the hold is reconciled, never dropped by aicrewd |
| Profile disabled while an attempt is running | the next team operation is refused with identity.v1's existing `context_stale` (the audited reason is the disabled profile); `team.read` shows the team disabled, `team show` says so, and the attempt is set `blocked` (reason: profile disabled) | the operator re-enables on the hub; aicrewd does not |
| `team.register` for a UUID the hub knows under another name | the profile is renamed to aicrewd's name (aicrewd owns it); grants, bound to the UUID, do not move; audited with both names | none needed; the operator reads the UUID that `grant` printed |
| `team.register` with a name another team of the peer holds | refused, `team_name_taken`; the team exists in aicrewd without a hub registration and `team check` says so | `aicrew team rename`, then re-register |
| Repository of a project changed while an attempt is running | the attempt keeps the six repository fields recorded at offer; aicrew guarantees this (aimem binds no repository to a hold); new offers take the new repository; members whose capabilities fall short are told (3.7) | none for the running attempt; the coordinator decides whether to withdraw it |
| Two granted projects on two instances of one forge | two requirements, two credentials, two files (`<host>.<account>.<purpose>` each); a deposit or `--cred` for one host never touches the other | none; a missing host is announced (3.7) |
| Forge host unreachable at `join` or `check` | that credential stays unverified and unprovisioned, named in the report; the others proceed | rerun `join --home <home>` or `check` when the host answers |
| Deposit delivery: response lost, or the home's write fails | the deposit stays undeleted and unacknowledged; `team check` lists it as pending | `join --home <home>` retries the completion step and receives the deposit again, to the same proven identity |
| Deposit acknowledged, then the home loses the file | gone from aicrewd by design; no second delivery | the operator deposits again on a `link` invitation, or hands a file to `join --cred` |
| Invitation expired or revoked with deposits pending | the deposits are deleted with it; audited | a new invitation with new deposits |
| Envelope issuance: aimem subcode issued, aicrewd refuses the invitation | nothing revealed; the console client prints the revoke command for the subcode | the operator revokes, retries with a new bundle |
| Envelope stolen and redeemed by someone else first | the thief holds the new hub user (no grants of its own), the membership and the forge deposits; the legitimate `join` fails with `enrollment_invalid` or a consumed invitation, which is the signal | the operator disables the user and revokes its credential, revokes the membership, revokes the forge tokens on their forges, issues a new envelope |
| Enrollment redeemed but the invitation step fails | the home holds its aimem bearer; nothing from aicrewd; the enrollment is not repeated | `join --home <home>` resumes at the invitation step while it is usable (ONBOARDING-CONTRACT retry); past its expiry, a fresh invitation (no envelope) for that agent |
| `join` rerun after partial provisioning | allowed on the linked home; each step is idempotent: enrollment skipped when the bearer exists, redemption resumed, deposits delivered if pending, `--cred` files verified and written per host; the report names what was already there | none |
| Triage write on a held task | refused, `task_held` | after release, or the coordinator withdraws the attempt first |
| Coordinated claim on a not-READY task | refused, `task_not_ready`, not retryable (the proof is spent), to the worker and to the coordinator's inbox | the coordinator triages to READY and offers again (a new step) |
| Capability reported but the token was revoked on the forge since | the offer passes the early check, the worker's own `check` at accept fails on the forge and the accept is refused by name; aicrewd updates the capability | the operator issues a new token, deposit on a `link` invitation |
