## 0. Why

The first pilot (2026-10-03) proved the trust chain and the attempt protocol end to end and stopped at the accept step on missing mechanisms, not on bugs in the mechanisms that exist. Every hand-off between members needed a human message, the worker had no official way to know which repository to clone and with which credential, the coordinator could not record its own triage, and the operator could not read the admin commands without an explanation. The product goal is a team that works without babysitting, onboarded by a handful of readable commands. This proposal turns the pilot's findings into design decisions.

## 1. Principles

1. **One owner per fact.** The aimem hub owns projects and everything that is a property of a project: its data, its process pin, its repository, and the access of teams to it. aicrewd owns teams, their names, members, attempts and the members' capabilities. A fact is declared once, where its owner lives, and read by the other side.
2. **A member learns everything from its home and its inbox.** No instruction that matters arrives by chat: the team's hub, projects, repositories and credential requirements are in the home; the task, repository and base of an attempt are in the offer.
3. **Credentials are per member and per purpose, and each is delivered by its issuer.** Every member has its own identity on the hub and on each forge the team's projects use; material lives only in the member's home under `creds/` and in its aimem installation; declarations never carry values. The aimem credential is delivered by aimem (3.9); forge credentials are delivered through aicrewd only as deposits with the custody rules of 3.8. What a token can do is decided by the forge; declarations state what is required so it can be checked before work, not at `git push`.
4. **Commands read as sentences.** Entity names are named flags; where an entity has an ID and a name, two explicit flags; names accepted wherever IDs are; one `--` style in both tools; one flag name for each recurring intent (read a secret, write a secret).
5. **No workaround ships as a procedure.** What the pilot did by hand (hand-copied tokens, typed start prompts, manual READY) is replaced by software or by an operator step that exists for a reason.
6. **No silent refusal.** Whatever is refused for a missing right or capability is refused by name, to the party that can act on it, with the command that fixes it.
7. **Capabilities never authorize.** A capability reported by a member (3.6) or read from the hub by aicrewd (2.3) is a planning fact that makes refusals early; the authority to act stays with the party that enforces it (the forge for tokens, the hub for grants, aimem for task writes). No reported capability grants anything.

## 2. Projects, repositories, teams

**2.1 A project has one repository, declared on the project in aimem.** `aimem project repo set --project <p> --kind github|gitea|gitlab --url <clone url> [--access read|write]` and `project repo clear`; `aimem project show --project <p>` prints repository, process pin and grants. `--access` defaults to `write` (branches and pull requests); `read` is for projects members only consult. The property carries no default branch: the forge owns it, and the coordinator reads it at offer time (3.5). The process repository stays a separate project property (`process select`, as today); its forge kind adds a read requirement. The credential kind a member needs follows from the repository's `--kind`; there is no separate credential declaration. Cross-repository work is tasks in each project with dependencies between them, as the AIForge work was run so far. Task 01a102f8-bb79 (aimem side).

**2.2 Team creation declares no projects; aicrewd owns the team's name.** `aicrew team create --name <team> --hub <alias>` creates the team in aicrewd and registers it on that hub through the peer operation `team.register` (2.3). The hub alias is one aicrewd knows from its configuration. The team name has one writer, aicrewd: the hub profile mirrors it, the hub offers no operator rename of a team profile, and `aicrew team rename` re-registers. Names are unique per peer; `team.register` refuses a name another team of the same peer holds (`team_name_taken`). Grants bind the profile's UUID, so a rename moves no grant; `aimem identity team grant` and `revoke` resolve `--team-name` within the peer and print the UUID they acted on, so the operator sees which profile received the project. Task 01a102f8-bb84 (aicrew) and the register operation in 01a102f8-bb79 (aimem).

**2.3 Project access is the hub's grant, read by aicrewd through two bounded peer operations.** `aimem identity team grant --peer <service> --team-name <team> --project <project>` is the only place a project is attached to a team; `revoke` detaches it; both stay hub-admin operations, never a peer's. aicrewd keeps no project or repository list of its own: the set of projects a team works on is the set of its grants, read from the hub. The two operations, each permitted to a peer credential issued for exactly that operation (identity.v1 rule since C6b):

- **`team.register`** (input: aicrew team UUID, name). Creates the profile for that UUID under the calling peer, or renames it. It acts only on profiles of the calling peer, never creates or touches a grant, never re-enables a profile the operator disabled, and never changes anything else on the profile. Refusals, each by name: `peer_forbidden` (credential not issued for this operation, or the UUID belongs to another peer), `team_name_taken` (another team of this peer holds the name), `profile_disabled` (the operator disabled this profile; the operator re-enables, aicrewd does not), `invalid_argument` (malformed UUID or name). Audit: peer, UUID, old and new name, outcome.
- **`team.read`** (input: aicrew team UUID, or none for all teams of the peer). Returns, for the calling peer's own teams only: the profile's UUID, name and enabled state, the granted projects, and for each granted project its repository (kind, url, access), its process pin and nothing else: no tasks, no members, no knowledge, no other peer's teams. A disabled profile is returned with `enabled: false` and no grants; an unknown UUID answers `not_found`; a credential not issued for this operation answers `peer_forbidden`. Audit: peer, UUID, outcome.

aicrewd calls `team.read` at offer time, at `team show`, at `team check` and in the reconciliation loop, caches the result for its planning facts (3.6, 3.7) and refuses an offer on a project the team is not granted with a readable code (`project_not_granted`). The hub answer at offer time is authoritative; the cache serves only `show` and the gap announcements. The inbox visibility rule of CREW-CONTRACT (messages scoped to the team's project set) keeps its meaning with the grants as the project set, read through `team.read`. `-project` disappears from `aicrew team create`.

**2.4 `aicrew team show` and `aicrew team check` are the health check of the whole setup.** `team show --team-name <team>` prints the team whole: hub, registration state on the hub, granted projects with their repositories, process pins and access levels (read from the hub), members with roles, session state and verified capabilities. `team check --team-name <team>` walks the chain and reports each link green or red with the fixing command: hub reachable, peer registered and `peer check` passing, team registered and enabled, every grant's repository and process pin resolvable, every member's capabilities against the requirements, pending deposits (3.8). `aicrew doctor` does the same for the service itself (configuration, token files, TLS, the aimem block, `/healthz`).

## 3. Credentials, identities, capabilities

**3.1 Every member has its own forge identity and token.** The operator creates it on the forge (GitHub: an account or App per member; Gitea and GitLab: a bot user) and issues the token with the rights the granted projects' repositories need. aicrewd holds no forge authority and mints nothing (a broker through a GitHub App is out of scope and would be its own proposal).

**3.2 `join` provisions every credential kind the team's granted projects require.** The aimem credential arrives through aimem's own enrollment (3.9). Forge material arrives either as deposits under the invitation (3.8, the normal path) or as files on the command line (`--cred github=<file>`, owner-only or `-` for a hidden prompt, the fallback for a machine the operator provisions by hand). `join` copies each kind to `<home>/creds/<kind>.token`. Before provisioning anything, `join` fetches the team's requirements from aicrewd and prints them against what it has ("team aiforge requires github (write), gitea (read); available: github; missing: gitea"); a missing forge kind is a warning in the report and in `agent.json`, not a stop. `agent.json` lists the kinds the home holds and the forge identity each authenticates as, never a value. Task 01a102e1-354c.

**3.3 `check` verifies each kind against the declarations** by a read-only call to the forge ("who am I") and, per granted project, a read of its repository and, for `write`, the token's push and pull-request rights as the forge reports them. It prints a table: project, repository, forge, required access, verified or missing. Only the member's machine can verify a token, since only it holds the value; aicrewd learns the result through the member's authenticated session (3.6). A home missing a forge kind is not blocked by that alone (see 3.6); a home missing the aimem credential is.

**3.4 Use is confined.** Clones made from the offer's repository get a per-clone credential helper that reads the member's file, and the member's commit identity derived from its forge identity. The value never appears in a URL, a global git configuration, process arguments, logs or chat.

**3.5 The offer names the repository and its base; the coordinator resolves the base.** Offer and independent claim carry `repository: {kind, url, access, default_branch, base_commit, branch}`. Kind, url and access come from the hub's project property (2.3); the coordinator's agent resolves `default_branch` and `base_commit` at offer time by a read of the forge with the coordinator's own forge credential (so the coordinator role requires the read capability of every granted repository, 3.6), and names `branch` by the existing attempt-branch rule of CREW-CONTRACT; an independent claim resolves them the same way with the claimer's credential. All six fields are recorded on the attempt at creation and never change for its lifetime (11). The coordinator chooses the task and the worker, not the repository. Task 01a102e1-354c.

**3.6 Capabilities make refusals early.** At `join`, `check` and session start the agent reports its verified capabilities (credential kinds, repositories, access level) to aicrewd, which stores them per member as planning facts (principle 7). The coordinator's `/crew-offer` shows which workers can take a task of that project; aicrewd refuses an offer to a worker that lacks the required capability, with a readable code naming the missing kind (`capability_missing`), before it reaches the inbox; the worker's own check is the last guard at accept. A missing capability never blocks the home or the member's other work. Task 01a102e1-354c.

**3.7 A changed requirement is announced, not discovered.** When a project is granted to a team or a project's repository changes, aicrewd notices in its reconciliation loop (it rereads `team.read` with the same cadence it reconciles steps) and, for every member whose capabilities fall short, puts a message in that member's inbox naming the project, the missing kind and the command (`aicrew-agent join --home <home> --cred <kind>=<file>`, or the deposit the operator should make), shows the gap in `aicrew team show`, and answers `aicrew team check` with the full list of gaps so the operator sees right after a grant who needs which token. Until the member adds the material, only offers that need it are refused, each by name. Task 01a102e1-354c.

**3.8 Forge deposits: a forge credential travels with the invitation, once, after the member is proven.** The operator attaches the member's forge credentials to the invitation instead of moving files between machines: `aicrew invitation issue --team-name <team> --role <role> --expect-user <user> --expires 72h --deposit github=<file> --output <envelope file>`. Only forge kinds can be deposited; the aimem credential never is (3.9). Custody and delivery:

- **At rest.** aicrewd stores each deposit encrypted with a key held by the service account outside the store directory, named in `aicrewd.json` (`deposit_key_file`), bound to the invitation and expiring with it. A dump of the store without the key yields nothing; the key file is owner-only and never leaves the host.
- **Delivery after proof.** The deposits are released only in the step after redemption has completed, that is after aicrewd has the aimem receipt that proves the member is the expected user (ONBOARDING-CONTRACT independent proof), over the same authenticated TLS session, to the agent whose identity the receipt established. A stolen invitation code alone therefore obtains no deposit: completion needs the member's own aimem credential, which the code does not carry.
- **Acknowledged delivery.** `join` writes the material into the home, then acknowledges; aicrewd deletes the deposit on the acknowledgment, not on sending. A lost response is retried: until the acknowledgment the deposit stays and `join --home <home>` (the existing completion retry) delivers it again to the same identity. Partial delivery is therefore distinguishable from success: a deposit still present means the member has not confirmed it, and `team check` lists it under pending deposits.
- **Audit and listing.** Every issue, delivery, acknowledgment, expiry and revocation is audited with invitation, agent, kind, time and outcome; `aicrew invitation show` lists deposits by kind and state, never a value.
- **Attacker outcomes.** Stolen code: nothing before completion, and completion is impossible without the member's aimem credential. Compromised aicrewd host with the key: the forge deposits pending at that moment, never a member's aimem bearer and never a delivered deposit (deleted). Compromised member session: its own home's material, as today.

An expired or revoked invitation takes its deposits with it. aicrewd holds a member's forge secret only between `invitation issue` and the acknowledgment of `join`; long-term storage stays in the member's home. Later additions (a new forge after a grant) use a deposit on a `link` invitation for that agent, redeemed by `join --home <home>`. Task 01a102e1-354c.

**3.9 The aimem credential is delivered by aimem (D1 enrollment), inside the same envelope.** The operator issues the member's aimem enrollment code on the hub (D1, `aimem identity enroll --user-name <user> --output <file>`); the console client on the operator's machine assembles the envelope written by `--output`: the aicrew invitation code and the aimem enrollment code side by side, never sent to aicrewd. The member receives one file. `join` reads it and runs in this order: redeem the enrollment code directly at the hub and store the bearer in the home's aimem installation; redeem the invitation at aicrewd and complete it with the receipt that bearer obtains; receive the forge deposits (3.8). The member still needs one code; aicrewd never sees the aimem secret, as ONBOARDING-CONTRACT already requires. `--aimem-token-file <file|->` stays as the fallback for a bearer issued by hand. Task 01a102e1-354c (aicrew); D1 is already approved on the aimem side.

## 4. Members act without a human message

**4.1 Wake-up.** The launcher, which already holds the inbox, wakes the client when a message arrives; a member never ends a turn waiting. Task 01a0d6d7-1aed (raised to prerequisite).

**4.2 Initial instruction.** `run` hands the client a managed first instruction (`/crew-start`) so the first turn reads the home guidance and the inbox without a typed message; `run -- <client args>` still passes extra arguments; an operator flag disables it for debugging. Task 01a102cc-3a60.

**4.3 Managed slash commands.** `join` writes the role's commands into the home, namespaced `crew-` and checked against the client's built-ins and the user's own skills: `/crew-start`, `/crew-inbox`, `/crew-offer`, `/crew-review`, `/crew-accept`, `/crew-submit`, `/crew-handoff`; generated from the same source as ROLES.md. Task 01a102d2-ef73.

**4.4 The home names its team's projects and hub.** Written by `join` from the hub's grants and aicrewd's team record; shown in START.md and by `session status`. Task 01a102cc-3a4b.

**4.5 Session rule.** Under `run` the launcher holds the session; `session start`, `session leave` and `run` refuse to execute from inside a launched client (the launcher's environment variables are present) and name `aicrew-agent inbox` as the next action; START.md step 5 says so. Task 01a102d0-0d7b.

## 5. Coordinator triage in team mode: decision (a), bounded

A coordinated claim requires the task READY; today a team session has no task write, so the pilot's coordinator could not record its own triage (PILOT-RUN-1, P7). Two options were compared; the operator chose **(a)** on 2026-10-04.

**5.1 The decision.** The coordinator role gets task triage authority in team mode through the team profile: state BACKLOG and READY in both directions, priority, size, `next_action`, and comments, on tasks of the projects the profile is granted. Bounds:

- **Held tasks are untouchable.** A task under a reservation (any member's, the coordinator's own included) refuses every triage write with `task_held`; the existing rule that generic writes are refused while held stays. Triage happens before a claim or after a release, never under a hold.
- **Authority is the grant.** The write is allowed only on tasks of projects granted to the team profile, and only when aicrewd's team-mode context names the member's role as coordinator; a worker's team session keeps `task_write: false`. The role is a fact aicrewd asserts about its own team; the hub trusts the peer for it, as it already does for the coordination facts.
- **Actor is the member.** aimem records the coordinator's user ID as the actor, as for every team write; the task history shows who triaged.
- **Partial update.** The aimem increment adds a partial task update (or a dedicated state transition) so a triage write never replaces the field set: the pilot's `update_task` cleared `epic` and `candidate_refs` (P7).
- **Readable refusal.** A coordinated claim on a not-READY task answers `task_not_ready` (status 409, retryable after triage, next action: the coordinator triages or withdraws) instead of `reservation_conflict`.

Task 01a102d9-440b (aicrew: the context aicrewd reports, `/crew-triage`), and an aimem task filed from this revision (the profile capability, `task_held`, `task_not_ready`, the partial update).

**5.2 Why (a), and what it costs.** The comparison the decision rests on:

| | (a) coordinator writes triage through the team profile | (b) the offer carries the READY assessment |
|---|---|---|
| Who may change task state in team mode | the coordinator, on unheld tasks of granted projects | nobody directly; aimem moves one task to READY as part of a claim it verifies against the aicrew offer |
| Proof required | the team session plus aicrewd's role assertion in the team-mode context | an aicrew-verified offer or independent claim naming that task; the assessment is bound to the fact, never taken from the claimer's body |
| Actor recorded | the coordinator's user ID | the coordinator from the verified fact, as for the claim |
| Held tasks | refused (`task_held`) | not reachable (a held task is already claimed) |
| What a compromised coordinator session can do | triage any unheld task of the granted projects: state between BACKLOG and READY, priority, size, next action, comments; no content edits beyond those fields, no held task, no other project | make READY exactly the task its own offer names, inside a fenced claim; nothing else |
| What it covers | all of triage: grooming, splitting, priority, returning to BACKLOG, before any offer exists | only "ready for this attempt"; the rest of triage keeps no path in team mode |
| Contract cost | context matrix coordinator row, team-mode report `task_write`, reservation.v1 `task_held`/`task_not_ready`, task API partial update | coordination.v1 amendment or new version after C5-w3 was declared the last in-place amendment, plus reservation.v1 `task_not_ready` |
| Board | shows triage as it happens; the board stays authoritative | shows BACKLOG until a claim lands |

(b) has the smaller reach for a compromised session. (a) was chosen because the pilot needed the whole of triage, not one transition, because the board must show the decision before an offer exists, and because (a) stays inside the existing authority model (grant plus role) while (b) couples aimem's coordination contract to aicrew's attempt semantics. The reach of (a) is bounded by the grant, the hold rule and the field list above, and recorded per actor.

## 6. Readable commands

**6.1 aimem admin commands** (`aimem identity …`, `aimem access …`, `aimem project …`): entity names are named flags (`--peer`, `--team-name`/`--team-id`, `--project`, `--user-name`/`--user-id`, `--group-name`/`--group-id`, `--operation`); a positional argument only where a command has exactly one entity (`aimem identity peer check <service>` stays); the old positional form kept one release with a notice; team profiles carry `team_name`; output prints names beside IDs; `--help` shows a full example. Vocabulary rules: `--project` is the long form everywhere and `-p`, which every project-taking command uses today, stays as its alias; `aimem project <verb>` is the namespace of the new commands (`repo set`, `repo clear`, `show`) while the existing `projects`, `project-id` and `drop-project` stay as they are, with their `aimem project …` forms added as aliases in the same release; `access grant` subjects that may be a group take `--group-name`/`--group-id` with the same exclusive rule as users. The selector rule (exactly one of name or ID) applies to looking up an existing entity; `create` and `rename` take the ID plus the new name. Task 01a102f8-bb79.

**6.2 aicrew commands** accept names wherever IDs are accepted (`--team-name pilot`, `--expect-user pilot-worker`), print both, and the documentation uses `--` for both tools.

**6.3 Names.** `service_id` names the deployment's service: `aicrew-service` for this deployment (renamed before the resume). `aicrew introspection-credential` becomes `aicrew hub-credential` (the credential this service issues to a hub), old name kept one release. Task 01a102ee-a2cd.

**6.4 One flag per secret intent, in both tools.** Writing a secret to a new owner-only file is always `--output <file>` (today `-code-file`, `-secret-file`, `-file` in aicrew and `--secret-file` in aimem); the file must not exist, is created readable by its owner only, and the value never goes to the terminal. Reading a secret is always `--token-file <file|->` (`-` reads standard input; a hidden prompt when standard input is a terminal is a nicety, not a requirement); attaching a forge secret to an invitation is `--deposit <kind>=<file>`. Old names kept one release with a notice. Covered by 01a102f8-bb79 (aimem) and 01a102ee-a2cd extended to the aicrew client (aicrew).

**6.5 Differences the aimem counterpart keeps.** So both texts move in step, the aimem design document may differ from this one only in these named places: `--admin-token-file` stays on hub-admin commands that read the admin token beside another token argument (the one exception to 6.4, named there); `aimem project repo show` may exist as a narrower alias of `project show`; `--token-file -` reads standard input (consistent with 6.4 as amended). The operator rename of a team profile is withdrawn (2.2). Any other difference is a defect in one of the two texts.

## 7. Target onboarding, once this ships

Once per project (owner of the data): `aimem project repo set --project <p> --kind github --url <url>` and `aimem process select … --project <p>`. Once per team: `aicrew team create --name <team> --hub <alias>`; `aimem identity team grant --peer <service> --team-name <team> --project <p>` per project (prints the UUID granted); `aicrew team check --team-name <team>` (for this deployment: a team `aiforge` granted `aicrew`, `aimem` and `aiskills`, all on GitHub, so one GitHub token per member covers them). Per member: a hub user, its aimem enrollment code (`aimem identity enroll --user-name <user> --output <f>`), a forge identity and token, then one command that carries all of it: `aicrew invitation issue --team-name <team> --role <role> --expect-user <user> --expires 72h --aimem-enrollment <f> --deposit github=<f> --output <envelope>`; the envelope goes to the member privately, nothing else does. Member, once: `aicrew-agent join --label <l> --url <aicrewd> --hub <alias> --client claude --envelope <file>`; `join` enrolls at the hub, redeems and completes at aicrewd, receives the forge deposits, provisions the home and ends `ready` with the capability table. Work: `aicrew-agent run --client claude --home <home>`; the client starts with `/crew-start`; the human merges pull requests and watches `aicrew team show`. What a machine then needs before the envelope: the installed binaries (aimem, aicrew-agent, the client) and an active account with the model provider for the client; everything else arrives at join.

## 8. Out of scope

Token minting or brokering by aicrewd; a shared project token; several repositories per project and multi-repository offers; several teams per home; OpenCode carriers and commands (1af8); event-driven delivery beyond the launcher's wake-up; a web console (a future client of the operator API); deleting hub profiles when a team is removed; depositing the aimem credential through aicrewd (3.9 replaces it).

Later, its own proposal: toolchain requirements (forge CLIs such as gh or tea, LSP servers, MCP servers, skills) declared at the organization level (the process manifest in aiskills, which is the company's development process), at the project level (language, forge), at the role level (coordinator and worker), and verified against the host by `check` with verified installers, as aimem and ai-skills are today. Also later: delivering the model provider's credential to the client from the home.

## 9. Order of delivery

aimem: 2.1 project repository property and `project show`, the `team.register` and `team.read` operations with their refusals (2.3), 6.1 and 6.4 (S together); the section 5 increment (profile triage capability, `task_held`, `task_not_ready`, partial update; S). aicrew next release: 6.3 rename, 6.4 flag names and 4.5 session rule (XS each); 2.2 to 2.4 and 3 together (team registration and names, `team.read` consumption, envelope with enrollment, forge deposits with custody, credential provisioning, capabilities, requirement announcements, health check, offer fields; M to L, split as the assessment proposes); 4.1 to 4.4 as one group (M); then 5 on the aicrew side (`/crew-triage`, the role in the team-mode context). Before the pilot resumes: rename the service to `aicrew-service`; re-select the process pins of `aicrew`, `aimem` and `aiskills` to the aiskills repository's GitHub URL (the process repository moved from the private Gitea); set each project's repository; `join` rerun per home; `run`; re-offer the pilot task.

## 11. Failure modes of the new mechanisms

| Situation | Outcome | Recovery |
|---|---|---|
| Hub unreachable, or `team.read` refused, at offer time | the offer is refused (`hub_unavailable` or the refusal's own code); nothing is sent to the worker; aicrewd never falls back to its cache for an offer | retry when the hub answers; `team check` shows the link red |
| Grant revoked while an attempt is running | aimem denies the next affected team operation (context contract lifecycle); the reservation is not released silently; aicrewd notices in reconciliation, marks the attempt `blocked: grant revoked` and tells coordinator and worker | the operator re-grants, or closes the attempt under the coordination contract's closure rules; the hold is reconciled, never dropped by aicrewd |
| Profile disabled while an attempt is running | as above, with `profile_disabled` on the next team operation; `team.read` shows the team disabled and `team show` says so | the operator re-enables on the hub; aicrewd does not |
| `team.register` for a UUID the hub knows under another name | the profile is renamed to aicrewd's name (aicrewd owns it); grants, bound to the UUID, do not move; audited with both names | none needed; the operator reads the UUID that `grant` printed |
| `team.register` with a name another team of the peer holds | refused, `team_name_taken`; the team exists in aicrewd without a hub registration and `team check` says so | `aicrew team rename`, then re-register |
| Repository of a project changed while an attempt is running | the attempt keeps the six repository fields recorded at offer; aicrew guarantees this (aimem binds no repository to a hold); new offers take the new repository; members whose capabilities fall short are told (3.7) | none for the running attempt; the coordinator decides whether to withdraw it |
| Deposit delivery: response lost, or the home's write fails | the deposit stays undeleted and unacknowledged; `team check` lists it as pending | `join --home <home>` retries the completion step and receives the deposit again, to the same proven identity |
| Deposit acknowledged, then the home loses the file | gone from aicrewd by design; no second delivery | the operator deposits again on a `link` invitation, or hands a file to `join --cred` |
| Invitation expired or revoked with deposits pending | the deposits are deleted with it; audited | a new invitation with new deposits |
| Enrollment code redeemed but the invitation step fails | the home holds its aimem bearer; nothing from aicrewd | `join --home <home>` resumes at the redemption step (ONBOARDING-CONTRACT retry); the enrollment is not repeated |
| `join` rerun after partial provisioning | allowed on the linked home; each step is idempotent: enrollment skipped when the bearer exists, redemption resumed, deposits delivered if pending, `--cred` files copied over; the report names what was already there | none |
| Triage write on a held task | refused, `task_held` | after release, or the coordinator withdraws the attempt first |
| Coordinated claim on a not-READY task | refused, `task_not_ready`, to the worker and to the coordinator's inbox | the coordinator triages to READY and re-offers |
| Capability reported but the token was revoked on the forge since | the offer passes the early check, the worker's own `check` at accept fails on the forge and the accept is refused by name; aicrewd updates the capability | the operator issues a new token, deposit on a `link` invitation |
