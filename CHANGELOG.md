# Changelog

All notable changes to aicrew are recorded here, in the
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) format, with
versions following [Semantic Versioning](https://semver.org/).

## [Unreleased]

Ordinary pull requests do not edit this file. The release-preparation pull
request writes the next `[X.Y.Z] - YYYY-MM-DD` section here, from the titles
of the pull requests merged since the last tag. A release's notes are that
section, and the release workflow refuses a tag that has none
(DEVELOPMENT.md, "Releasing").

### Added

- **The pilot simulation's stack** (01a17d9a-932b, increment I1).
  `scripts/pilot-sim.sh` brings up the hub, aicrewd, Gitea and two member
  homes in containers, each installed and joined the way the operator
  does it, with real TLS and no typed input, and checks that both members
  are green, listed and serving (docs/E2E-PILOT-SIM.md). The b4 harness's
  CA code moved to `e2e/testca`, unchanged, so both share it.
- **A headless member joins without a terminal** (01a17d8e-4255).
  `aicrew-agent join --code-file PATH` reads the invitation code from a
  file readable by its owner only, and `--code-file -` from one line of
  standard input when that is not a terminal (the hidden prompt when it
  is). The code is never an argument: a value that is not a file is
  refused without being quoted. A malformed code from a file or a pipe is
  refused at once instead of asked again. Without the flag and without a
  terminal, join still stops with `no_terminal`, now naming `--code-file`.
- **The member one-liner installs prebuilt binaries** (01a17d8e-4267).
  `AICREW_PREBUILT_DIR=DIR boot.sh` installs `aicrew-agent` and `aicrew`
  from DIR instead of downloading a release, as `install-aicrewd.sh`
  already does for aicrewd. A `SHA256SUMS` in DIR is checked when present.
  A missing binary or a hash mismatch installs neither, and the services'
  stop and start around an upgrade run as before. For an unreleased build
  and for a closed network. `boot.ps1` does not have the knob yet.
- **The aicrewd installer has an install-only mode** (01a17d8e-427b).
  `AICREW_NO_SERVICE=1 install-aicrewd.sh` installs and upgrades aicrewd on
  a host or container without systemd. It skips linger, the unit, the start
  and the health wait, never calls `systemctl` or `loginctl`, and prints the
  `aicrewd -config` command a supervisor runs as the service user. An
  upgrade refuses while aicrewd still answers, because it cannot stop it. A
  failed swap or migration still restores the binaries, the configuration
  and the store. The default mode is unchanged.

### Changed

- **A write aimem refuses as unreadable text is a correction, not a
  failure** (01a17698-f6c3). aimem 0.10.14 refuses a task comment or a
  task field whose prose breaks its writing rule with `unreadable_text`,
  naming the field, the flagged words and the fix. The refusal reaches the
  member's model as the tool's result, and the turn goes on: it never fails
  the turn, holds the member or blocks the attempt. ROLES.md's "Writing
  that others read" now tells the member to rewrite the text as the fix
  says and send it again in the same turn. A `join` rerun brings the line
  to a home.
- **The documents match the code again** (01a17737-425e), from the manual
  pass of the examples check:
  - WORKSPACE.md states the instruction precedence as the managed START.md
    does and names it as the authority;
  - WORKSPACE.md and DEVELOPMENT.md name the two hooks the client wiring
    installs, the Stop hook and the command guard;
  - CREW-CONTRACT.md lists the session attempt's `base_commit`, `process`
    and `repository`;
  - DEVELOPMENT.md drops the clone note that waited for the attempt's
    repository, and names two more limits of the examples check.

  The check itself now keeps the words after a `$(...)` substitution with
  the invocation around it, so a stale flag there is reported.
- **The command guard passes a `find -delete` narrowed by name at the
  working directory** (01a17697-e272). `find . -name '*.tmp' -delete` used
  to be refused like `find . -delete`. It now passes when a `-name`,
  `-iname` or `-path` test whose pattern holds more than wildcards, dots
  and slashes comes before the first `-delete`, with no `-o`, `-or`, `,`,
  `!` or `-not` before the last one. find's leading options (`-L`, `-P`,
  BSD's `-f <start>` and the like) and `--` are skipped to find the real
  start, and without a start word after them only a find that goes on with
  its name test passes. `find . -delete`, `find . -type f -delete` and
  `find . -name '*' -delete` stay refused, now with advice that fits:
  narrow it by name, start in a subdirectory, or use `-exec rm {} +`.
- **The guard records the wrapped scripts it could not read**
  (01a17697-e286). A wrapper whose script runs a program the guard cannot
  read, such as `sh -c "$CMD"`, `eval "$X"` or `powershell -Command $s`,
  still passes, and now writes a line with the rule `unjudged` to
  `logs/guard.jsonl`, so the log counts every command the guard passed
  without judging it.
- **The tested ai-skills release is 1.33.13** (01a18173-b005), up from
  1.26.1; the minimum stays 1.26.1. Its installer writes the
  `.ai-skills.json` record check reads (ai-skills writes it from 1.28.0
  on), so a home installed as check instructs reports ai-skills
  `supported` instead of `unknown`. The pilot simulation's smoke check
  now requires `supported` at the tested release. An installation from
  a release before 1.28.0 still has no record and is still `unknown`, a
  notice that does not block.

### Fixed

- **check's ai-skills instruction runs the installer through bash**
  (01a18173-b01e). The command `aicrew-agent check` prints to install
  ai-skills ended in `./src/install.sh`, which fails with "Permission
  denied" on Linux and macOS when the release archive stores the script
  without its execute bit, as ai-skills 1.26.1 does. It now reads
  `bash ./src/install.sh`. The pilot simulation found it, and its member
  image now runs the command as printed.

## [0.8.0] - 2026-10-27

Twelve pull requests since 0.7.0 (#200 to #211). A member's hold now
reaches the team's coordinators once and shows in `aicrew status` (#200).
A command guard in each member home refuses destructive git commands and
recursive deletes beyond the member's own work (#206). `check` and `serve`
verify the turn model before the first turn (#205). The operator reads an
attempt's handoff, and the coordinator sees when it was pushed (#203).
Beside these come exact bounds for the turn brief (#201), a turn record
that names the brief's messages (#202), the Windows one-liner in both
forms (#204), a CI check of the documentation's examples (#207), the
toolchain's `cd` allowed in `/crew-turn` (#208), the real-aimem harness
passing again with a workflow that runs it (#209, #210), and two server
tests that no longer depend on the wall clock (#211).

The store moves from schema 38 to schema 39. The hub goes first: an older
aicrewd refuses the newer store, and going back to 0.7.0 means restoring
the store copy the upgrade made. aimem 0.10.0 or later stays required;
this release is tested with aimem 0.10.13. The pilot team stays paused:
nothing in this release resumes it.

### Breaking changes

- **The store schema is 39** (#200: `member_holds` and
  `member_hold_announcements`). The hub one-liner migrates it. An older
  aicrewd refuses a schema-39 store with `store schema is newer than this
  build`, and a downgrade restores the upgrade's copy
  (`<store>.backup-<UTC time>`), losing what was written since.
- **aicrewd before the members** (#200). A 0.8.0 launcher reports its
  member's holds to `POST /v1/crew/holds`. A 0.7.0 aicrewd answers
  `not_found`; the launcher then keeps the hold local and logs once that
  the coordinators are not told.
- **The managed settings install a command guard** (#206).
  `aicrew-agent guard --home HOME` runs as a PreToolUse hook (matcher
  `Bash|PowerShell`) in both wake modes. On any branch it refuses forced,
  deleting or mirroring pushes, `--no-verify`, history rewrites and the
  deletion of the default branch. On main, master or the default branch it
  also refuses `reset --hard`, `clean -f`, a whole-tree checkout or
  restore, `stash drop` or `clear` and `commit --amend`. A recursive delete
  is refused when it reaches outside the directory the call starts in. The
  refusal says what to do next. A command whose branch git cannot tell
  passes and is logged in `logs/guard.jsonl`. It is a safety catch, not a
  sandbox. `agent.json` `"guard": {"off": true}` turns it off for one
  member. A `join` rerun brings the hook to a home; see the upgrade steps.
- **`serve` refuses an unserved turn model** (#205). Before taking the
  session, `serve` makes one minimal call with the home's `turns.model`.
  A model the provider does not serve refuses the start with exit 2 and
  an instruction naming `turns.model`, so a service does not restart into
  it. A turn that meets an unserved model ends as `model_unavailable` and
  holds the member as for `needs_login`.
- **`/crew-turn` allows one compound command** (#208): the project's build
  and test commands in the attempt's worktree, as `cd worktrees/NAME &&
  COMMAND`. Every other `cd`, `&&`, `;`, pipe and redirection stays
  forbidden. A `join` rerun brings the command to a home.

### Upgrade steps

All of them use product commands and one-liners. The hub goes first.

1. **aicrewd.** On the hub host, as root, run the hub one-liner:

   ```sh
   curl -fsSL https://raw.githubusercontent.com/BlackVS/aicrew/v0.8.0/install-aicrewd.sh | bash
   ```

   As before, it backs up the configuration and the store, swaps the
   binaries, migrates the store to schema 39, waits for health at 0.8.0,
   and rolls back if the new release does not come up. The holds and
   attempt-handoff routes come with it.
2. **The operator's machine and each member.** As that user, rerun the
   member one-liner, which stops the account's registered member services,
   swaps the binaries and starts them again:
   - Linux and macOS:

     ```sh
     curl -fsSL https://raw.githubusercontent.com/BlackVS/aicrew/v0.8.0/boot.sh | bash
     ```

   - Windows, in a PowerShell window that is already open:

     ```powershell
     irm https://raw.githubusercontent.com/BlackVS/aicrew/v0.8.0/boot.ps1 | iex
     ```

   - Windows, from cmd or the Run dialog:

     ```powershell
     powershell -NoProfile -ExecutionPolicy Bypass -Command "irm https://raw.githubusercontent.com/BlackVS/aicrew/v0.8.0/boot.ps1 | iex"
     ```

3. **Each home.** Rerun `aicrew-agent join --home HOME`. The rerun
   refreshes `.claude/settings.json` (the guard hook) and the crew commands
   (the new `/crew-turn`). An edited file is kept, with the new version
   written beside it with the suffix `.aicrew-new`.
4. **Check each home.** `aicrew-agent check --home HOME` now probes a turns
   home's model and prints it as `turn model: CONFIGURED -> RESOLVED
   (STATE)`, blocking with `turn_model_unavailable` when the provider does
   not serve it. It notes a missing guard hook, one naming another binary,
   and a guard turned off.

### Holds

- **A member's hold reaches the coordinators once** (#200). The launcher
  reports a spent attempt budget, a spent daily budget, the provider's
  limit and a missing login to `POST /v1/crew/holds`, and the first
  admitted turn clears it. aicrewd writes one lifecycle message to the
  team's active coordinators per hold identity: the attempt for its
  budget, the UTC day for the daily budget, and the reset time or the day
  for a limit or a login. The same identity reported again tells no one.
- **`aicrew status` shows the hold** with the amount, the limit and the
  next check, or the login command (`opapi.MemberState.hold`).
- **`budget.spent`** is journaled for a spent budget, in the hold's own
  transaction. No default subscription names it. `CREW-CONTRACT.md`
  describes the route ("A member's hold").

### Attempts and turns

- **The operator reads an attempt's handoff** (#203) with `aicrew attempts
  handoff --id ATTEMPT [--json]`, over `GET /v1/admin/attempt/handoff`
  (the operator or an architect credential). The coordinator's open
  attempts and the team state carry `handoff_updated_at`, and the
  open-attempts line says "handoff pushed TIME" or "no handoff pushed".
- **The turn brief's bounds are exact** (#201): a cut with no room for its
  ellipsis is empty, so a task snapshot stays within its bound.
- **The turn record names the brief's messages** (#202):
  `brief_messages`, and `brief_messages_unacted` for a turn that did not
  finish. A message's delivery count means "handed to a turn's brief or
  read by the member", not "acted on".
- **The turn model** (#205): `check` reports `turn_model` and `serve`
  probes before the first turn, as above. `docs/TURN-PROBE.md` records the
  client's answer for an unserved model.

### Docs

- **The Windows member one-liner in both forms** (#204): the bare `irm ...
  | iex` for a PowerShell window that is already open, and the
  `powershell -NoProfile ...` form for cmd or the Run dialog, which a host
  policy may refuse from inside PowerShell.
- **The documentation's examples are checked against the code** (#207):
  every `aicrew`, `aicrew-agent` and `aicrewd` command and flag, every
  aicrewd route and every automation builtin named in `README.md`, `docs/`
  and the home's managed documents (`scripts/check-doc-examples.sh`, run in
  CI). The manual pass corrected the repository and worktree paths in
  `WORKSPACE.md` and a `team grant` line in `DEVELOPMENT.md`.

### CI and tests

- **The real-aimem harness passes its whole matrix again** at the pinned
  aimem (#209, #210). Scenario H selects a process aimem reads without the
  network; B1 waits out the event queue's quiet and reads `action.needed`;
  F1's network faults hold for the whole step, past the replay in aimem's
  HTTP client. The new `e2e-real-aimem` workflow runs it nightly on main
  and by hand on any branch; a release-preparation pull request needs a
  green run at its head.
- **Two server tests no longer depend on the wall clock** (#211), through
  `Store.SetClock` and a clock for the grants reads, both unset in
  production.

## [0.7.0] - 2026-10-23

Increment 3 of the turn-economics design (`docs/DESIGN-TURNS.md`), merged
as 11 pull requests since 0.6.0. Every turn now starts fresh from a brief
the launcher writes, and no conversation is resumed (#189). A worker's
`docs/HANDOFF.md` carries the attempt from turn to turn, and aicrewd keeps
a copy of it (#190, #191). Each turn's cost is reported to aicrewd, so the
budgets hold in a new home (#192). A turn reads only the rules for its
kind, and the coordinator gets a brief of its own (#193). Beside these
come a check warning about the OS user's own Claude Code configuration
(#195), two fixes to the workflow automations (#197, #198), a probe of the
turns' starting context (#188), mode-neutral repository instructions
(#194) and a hang test that holds under load (#196).

The store moves from schema 36 to schema 38. The hub goes first: an older
aicrewd refuses the newer store, and going back to 0.6.0 means restoring
the store copy the upgrade made. aimem 0.10.0 or later stays required;
this release is tested with aimem 0.10.13. The pilot team stays paused:
nothing in this release resumes it.

### Breaking changes

- **The store schema is 38** (#190 schema 37: `attempt_handoffs`; #192
  schema 38: `turn_reports`). The hub one-liner migrates it. An older
  aicrewd refuses a schema-38 store with `store schema is newer than this
  build`, and a downgrade restores the upgrade's copy
  (`<store>.backup-<UTC time>`), losing what was written since.
- **No turn resumes a conversation** (#189). The per-attempt and
  per-member conversations, their rotation (50 turns, 70 % context, a new
  day) and the failed-resume reset are gone. Each turn gets its own
  session ID and starts from the brief the launcher writes: the attempt's
  state, who and where, the task as it was frozen at the attempt's first
  turn (`state/attempts/<attempt>/task.json`), why this turn with the
  pending messages' content, and the pull requests as the forge watch last
  saw them. A turn's cost is the client's total for its own conversation.
  An attempt that is open across the upgrade continues from the brief and
  its handoff section; what its earlier conversation knew is not carried.
- **The worker's `docs/HANDOFF.md` is the attempt's memory** (#191). The
  launcher opens a CURRENT ATTEMPT section for the open attempt and moves
  the section of a closed attempt into an Archive (the last 10 attempts,
  16 KiB). It keeps a ledger of one line per turn in
  `state/attempts/<attempt>/ledger.jsonl` (the last 50). The brief carries
  the section and the ledger. Two finished turns in a row that make no
  step and leave the section unchanged block the attempt (the stall rule);
  the three-turn rule stays. The rest of the file stays the agent's.
- **aicrewd keeps the attempt's handoff** (#190, #191). After a worker's
  turn the launcher pushes the doc when it changed, redacted and at most
  32 KiB, to `POST /v1/crew/attempts/{id}/handoff`. A home without the
  attempt's section takes aicrewd's copy, so a new home continues the
  attempt.
- **The budgets are checked against aicrewd's totals** (#192). The
  launcher reports each turn's cost to `POST /v1/crew/turns`, and keeps
  the reports that did not arrive (at most 50) to send again before the
  next turn. A home with no figure for the day or the attempt reads
  `GET /v1/crew/turns/totals` and keeps the larger of each. The thresholds
  and `--max-budget-usd` are unchanged.
- **A turn reads only the rules for its kind** (#193). `docs/ROLES.md` is
  written by section per turn kind (the coordinator; a worker's offer,
  running attempt and review result; an independent member), the brief
  names the sections for the turn's kind, and `/crew-turn` reads no
  managed doc in full. `START.md` puts the operator's instruction first,
  then the home's docs and the process, then a repository's `AGENTS.md`
  or `CLAUDE.md`. A `join` rerun brings these files to a home; see the
  upgrade steps.
- **The run log keeps every `pr()` and `attempt()` read in order** (#198).
  A run's end record in `logs/automations.jsonl` carries `prs` and
  `attempts` (at most 16 each, with `prs_dropped` and `attempts_dropped`
  when more were read) in place of the single `pr` and `attempt`. A log
  written by 0.6.0 still replays as before; replay a 0.7.0 log with the
  0.7.0 `aicrew`.
- **aimem 0.10.13 is the tested release.** 0.10.0 or later stays
  required; a newer aimem is reported by `aicrew-agent check` as newer
  than the tested one, as before. The real-aimem e2e harness pins
  v0.10.13.

### Upgrade steps

All of them use product commands and one-liners. The hub goes first.

1. **aicrewd.** On the hub host, as root, run the hub one-liner:

   ```sh
   curl -fsSL https://raw.githubusercontent.com/BlackVS/aicrew/v0.7.0/install-aicrewd.sh | bash
   ```

   As before, it backs up the configuration and the store, swaps the
   binaries, migrates the store to schema 38, waits for health at 0.7.0,
   and rolls back if the new release does not come up. The handoff and
   turn-cost routes come with it.
2. **The operator's machine and each member.** As that user, rerun the
   member one-liner, which stops the account's registered member services,
   swaps the binaries and starts them again:
   - Linux and macOS:

     ```sh
     curl -fsSL https://raw.githubusercontent.com/BlackVS/aicrew/v0.7.0/boot.sh | bash
     ```

   - Windows:

     ```powershell
     powershell -NoProfile -ExecutionPolicy Bypass -Command "irm https://raw.githubusercontent.com/BlackVS/aicrew/v0.7.0/boot.ps1 | iex"
     ```

3. **Each home.** Rerun `aicrew-agent join --home HOME`. The rerun
   refreshes `docs/ROLES.md` (now by turn kind), `docs/START.md` (the
   instructions' precedence) and the crew commands (the new
   `/crew-turn`). An edited file is kept, with the new version written

   `docs/HANDOFF.md` is kept: the launcher adds its sections, and a home
   joined before this release keeps the attempt's archive from aicrewd.
4. **Check each home.** `aicrew-agent check --home HOME` now warns when
   the OS user's own Claude Code configuration reaches the member's turns

   agent home per OS user; on a development station that shares the
   operator's account, what reaches the turns is the operator's
   responsibility.

### Fresh turns (increment 3: #189 to #193)

- **The turn brief** (#189). The prompt is `/crew-turn` followed by the
  brief on the client's standard input. The brief is redacted as a whole,
  at most 24 KiB, and keeps a pull request's observed review and checks
  across polls that read no content.
- **The attempt's handoff on aicrewd** (#190). Store schema 37 adds
  `attempt_handoffs`. `POST /v1/crew/attempts/{id}/handoff` replaces the
  doc of the member's running attempt (at most 32 KiB of UTF-8; refused
  with `attempt_state` once a stop is requested or the attempt is not
  running), and `GET` returns it to the attempt's worker in any state.
  `CREW-CONTRACT.md` describes both ("The attempt's handoff").
- **The session doc, the ledger and the stall rule** (#191), as above.
  A new attempt's directory under `state/attempts/` removes other
  attempts' beyond the newest 20, never the open one's.
- **The turns' costs on aicrewd** (#192). Store schema 38 adds
  `turn_reports`, one row per turn, idempotent by the turn's ID; the day
  is aicrewd's UTC date at the first receipt. `GET
  /v1/crew/turns/totals[?attempt_id=]` returns the member's total today
  and the attempt's. A launcher talking to an older aicrewd, which answers
  `not_found`, keeps its home's own figures. `CREW-CONTRACT.md` describes
  the routes ("The turns' costs").
- **The lean start by turn kind** (#193). The coordinator's brief carries
  the team's open attempts and its own `docs/HANDOFF.md`, cut at 8 KiB.
  `ROLES.md` and `/crew-turn` carry the repetition rule: a worker proposes
  "automate X" in its handoff and its pull request, and the coordinator
  posts it as an `[automate]` task comment. The interactive mode (`run`,
  `/crew-start`) reads `START.md` and `ROLES.md` as before.

### Workflow automations

- **A held base update runs when the last running check ends** (#197).
  When a check fails while another still runs, the aggregate conclusion is
  already `failure`, so no `after-ci` came when the last one ended and the
  update the external review held waited for the next head. A
  `forge.changed` event now carries `checks_settled` when the last running
  check concluded at the same head, and the `base-update` default acts on
  it when a check failed. `after-ci` keeps its meaning. The running state
  is read from each check run and commit status by the launcher's poll and
  stays inside the launcher.
- **`aicrew automation replay` answers the reads in order** (#198). The
  Nth `pr()` or `attempt()` read gets the run's Nth answer, so a script
  that reads the pull request, labels it and reads it again does what the
  run did. A read past the recorded ones answers the last again, and the
  output says so; recorded reads the replay did not make are listed.

### Check

- **The OS user's own Claude Code configuration** (#195), as in the
  upgrade steps. `aicrew-agent serve` logs the same warning at start.

### Docs

- **`docs/TURN-PROBE.md`** gains "The starting context of a turn" (#188):
  the starting context and cost of the resumed turns of 0.6.0, from the
  pilot's records, as the baseline for the fresh turns.
- **The repository's `AGENTS.md` and `CLAUDE.md` are mode-neutral**
  (#194): the place of launch sets the mode and the identity, and a team
  member follows its home's docs and the process where they differ.

### CI and tests

- The client-hang check test gives Claude Code's init probe its own
  ceiling, so the test holds on a loaded runner (#196).

## [0.6.0] - 2026-10-19

The first two increments of the turn-economics design
(`docs/DESIGN-TURNS.md`, section 14), merged as 27 pull requests since
0.5.9. Increment 1 is the event core: one journal on aicrewd, the board,
the forge, aicrewd itself and timers as its sources, subscriptions as data,
and the `action.needed` message that carries what a member has to decide,
so only a change that needs judgement wakes a model (#162 to #165).
Increment 2 is the workflow automations: Starlark scripts in a limited
child process with the host API of the design's 10.3, six extension points
in the launcher, declared commands at a point, the release's default
automations `base-update`, `gates-green`, `review-request` and `ci-rerun`,
a process manifest that overrides them by name, and `aicrew automation
replay` against a member's run log (#166 to #186). The public/instance
boundary design is recorded (#179), and the CI's race pass runs as jobs
of its own (#160, #161).

The store moves from schema 32 to schema 36. The hub goes first: an older
aicrewd refuses the newer store, and going back to 0.5.x means restoring
the store copy the upgrade made. aimem 0.10.0 or later stays required;
this release is tested with aimem 0.10.8. The pilot team stays
paused: nothing in this release resumes it.

### Breaking changes

- **The store schema is 36** (#163 schema 33: `events`, `event_deliveries`,
  `event_runs`; #164 schema 34: `attempt_blocks`, `timers`; #165 schema
  35: `messages` rebuilt for the `action.needed` kind, every row kept;
  #169 schema 36: `attempt_automation_runs`). The hub one-liner migrates
  it. An older aicrewd refuses a schema-36 store with `store schema is
  newer than this build`, and a downgrade restores the upgrade's copy
  (`<store>.backup-<UTC time>`), losing what was written since.
- **Only a change that needs a decision wakes a member** (#165). A
  forge change is delivered as an `action.needed` message with its
  content when the review at the head asks for changes, CI failed, a
  declared check failed at the head, both gates are green, or the pull
  request was merged, closed or reopened; progress alone wakes no one.
  A member reads what to decide in the message, not in the forge.
- **The gates wake is withheld where the launcher submits itself**
  (#172). With the `gates-green` default in the effective set, the
  launcher marks the pull request ready when both reviews and CI are
  green; the worker is woken for its gates only when that default is
  disabled by the process manifest.
- **A blocked report carries its reason** (#164). A worker's blocked
  report keeps its reason and its time on the attempt and wakes the

### The event core (increment 1: #162, #163, #164, #165)

- **`aicrew-agent forge pr show` prints the content** of a pull request:
  the checks with their conclusions, the failed jobs' log excerpts and the
  comments, besides its state (#162).
- **One event core on aicrewd** (#163). The journal keeps every event, its
  deliveries and its handler runs. The board wake and the forge events
  are its first sources; subscriptions are data with a published schema
  (`internal/events/subscriptions.schema.json`), and delivery
  deduplicates and coalesces: a burst of events about one subject wakes
  once, and a crash replays a run whole or not at all.
- **The timer and aicrewd sources** (#164). A `timer.due` event fires at
  its time; an attempt's blocked report is an event that keeps its reason
  and its time on the attempt (`aicrew team state` shows them) and wakes
  the coordinators.
- **`action.needed` with its content** (#165). A member is woken with the
  decision it has to make and the facts it needs, read from the journal;
  a change that needs no decision is handled by nobody.

### Workflow automations (increment 2: #166 to #186)

- **The Starlark sandbox** (#166, #167, #173). A script runs under a step
  limit, a wall clock and an OS memory limit (a job object on Windows, an
  rlimit elsewhere) in its own process, `aicrew-agent automation run`,
  with no file, network or environment access. Its host API is the
  design's 10.3: `pr()`, `attempt()`, `run()` under the turn's allow list,
  `step()`, `comment()`, `label()`, `ready()`, `submit()`, `rerun()`,
  `update_base()`, and `turn()` as a return value. The host calls reach
  the launcher over the step socket; no credential reaches the child.
- **Sources and precedence** (#168). An automation comes from the process
  manifest at the attempt's pin, from the repository's `automations/` at
  the base branch's merged commit, or from the release's embedded
  defaults; a manifest entry replaces, disables or adds a name. The
  entries and the script header have published JSON Schemas versioned with
  the host API. The set reloads on a pin or base change without a
  restart, and `aicrew-agent check` lists it.
- **The extension points** (#169, #170, #174, #177, #178). The launcher
  dispatches at `after-push`, `after-ci`, `ci-failed`, `gates-green`,
  `before-submit` and `after-merge`, at least once per edge: a point it
  could not prepare, or a run its own exit cut, fires again. A declared
  command at a point runs in the attempt's worktree under the allow list
  and is recorded with its exit status and output; one that fails after a
  push wakes the worker with the command and its output, and a worker
  failing the same check head after head is escalated to the coordinators
  past a bound. A command cannot set a credential helper or an askpass
  through its arguments (#175). A wake whose queue holds a failed run and
  a turn is one message per role (#176).
- **The pull request's transitions as host functions** (#171): `label()`,
  `ready()`, `submit()` and `rerun()`, performed by the launcher with the
  member's credential; a forge re-run happens once per head.
- **The defaults** (#172, #180): `review-request` adds `review-this`
  after a push and again when the external review fails to run,
  `ci-rerun` re-runs a failed check once per head, `gates-green` marks
  the pull request ready when both reviews and CI are green. The launcher
  also dispatches scripts on `forge.changed`, so a script subscribed to
  events runs on a change that needs no decision.
- **The base update as a host function** (#182, #183, #184).
  `update_base()` merges the base into the attempt's branch, computes the
  patch identity against the merge base, pushes, and posts the delta
  note; a conflict comes back to the worker as the content of a `fix`
  turn. The `base-update` default runs at `after-ci` and when the external
  review that held it ends, skips a head under review, and completes an
  update that a launcher's exit cut between its push and its note. Each
  effect is recorded in the run log, so the recovery reads the record,
  not the forge alone.
- **`aicrew automation replay --script FILE --events LOG`** (#186). The
  launcher's run log, `logs/automations.jsonl`, records on each run's end
  record the event the run was for and the facts `pr()` and `attempt()`
  returned, redacted as the script saw them; the operator replays a script
  against it with a recording host that performs nothing and prints, per
  event, the actions the script would take and how it ended.

### A member runs as a user service (#155)

- **`aicrew-agent service install|uninstall|start|stop|restart|status
  (--home HOME | --all) [--json]`** runs a home's turn loop as a service of
  the member's own account, with no elevation. Each home gets one service,
  `aicrew-member-<label>-<hash of the home path>`, listed in a per-user
  registry for `--all`.
  - **Linux:** a systemd user unit. It restarts the loop after a failure
    but not after a refusal (exit 2), and carries the `PATH` that
    `install` ran with. `install` notes when lingering is off.
  - **macOS:** a launchd agent with `RunAtLoad`, kept alive after a
    failure.
  - **Windows:** a logon task that runs the loop windowless through
    `conhost --headless`, with the member's interactive token, never twice
    at once.
- **join** installs and starts the service of a ready home in turns mode.
  `--no-service` or `AICREW_NO_SERVICE=1` leaves it out. join's last line
  names the service.
- **One serve per home.** `serve` holds `state/serve.lock` for its whole
  life and records its process ID in `state/serve.pid`. A second serve of
  the same home is refused. Ending a Windows task leaves its child
  running, so there `stop` ends the serve's own recorded process, never
  one found by name. `serve --log FILE` also writes the log to a
  file; the service uses `logs/serve.log`.
- **The member one-liner** (`boot.sh`, `boot.ps1`) stops the registered
  services with the new binary, swaps the binaries, and starts the
  services with the installed one, which rewrites each definition with its
  own path. `AICREW_NO_SERVICE=1` leaves them alone.
- **`check`** reports the home's service, with a `to do:` line when a home
  in turns mode has none, a stopped one, or a serve started by hand.

### A turn records its own cost and its metrics (#158)

The first increment of `docs/DESIGN-TURNS.md`. Claude Code's result
reports `total_cost_usd` and `modelUsage` as running totals of the whole
conversation; only `usage` is the turn's own.

- **A price list** of confirmed prices only. Today that is
  `claude-opus-5-5`: $4, $20, $0.20 and $8 per million tokens for input,
  output, cache read and 1-hour cache write.
- **A turn's own cost** comes from one of three sources, recorded as
  `cost_source`:

    is its own `usage` at list prices. `price_list` names the list's

  turn's own calls used, the tokens by kind with the cache write split

  steps and the outcome.

### Forge events wake members (A6)

- **The launcher watches the attempt's pull request** (#139). Every

  wait and every 60 seconds after. aicrewd still holds no forge credential

  wait: a label added, CI concluding success or failure, a new comment, a
  merge, a close or a reopen. It goes to the worker, and to the

- **Turns mode** (#141). `agent.json`'s `wake.mode` is `stop-hook` (the

  turn starts with. `check` notes a Stop hook left in a turns home, and each
  `turns.allow` rule it leaves out.

  does and runs one headless Claude Code turn at a time:
  - a turn starts when the member has unacknowledged messages, or when a
    worker's attempt is still in work after its last turn; never while the
    member or its team is paused, and at most one start per 5 seconds;
  - each attempt has one conversation that its later turns resume; other
    turns resume the member's conversation until 50 turns, 70 % of the
    context window, or a new UTC day;

    `max_continuations` come from `agent.json`'s `turns` object until A5. A
    provider limit, a login failure or a failed turn holds the member for
    a growing time;

    block the attempt, which tells the coordinator;

    owner-only on the host under `logs/turns/`;

  members; a re-grant clears it (#92).
- Members report their forge capabilities through their launcher. An offer
  checks the worker's, and `GET /v1/crew/capabilities` lists them (#93).
- A task that is not READY is refused by name (`task_not_ready`), whether
  aicrewd's own check or aimem's refusal answers. The coordinator triages
  with aimem's `triage_task`. An independent claim of a non-READY task is
  closed and announced to the team (#96).

### Members' credentials and repositories

- `aicrew-agent join --cred`, given a forge's host and a token file,
  verifies the token ("who am I"), writes it owner-only under `creds/` and
  records the account, never the value. `check` verifies every credential
  and prints the table. `step offer|claim --repository` fills an empty base
  commit from the forge (#88).
- `aicrew-agent clone` clones an attempt's repository into `repos/` and
  makes its worktree. The clone's own credential helper
  (`aicrew-agent git-credential`) answers git on a pipe, so the token never
  appears in a URL, a configuration, an argument or the output. Commits
  carry the member's forge identity (#89).
- `aicrew-agent digest` fetches an offer's pinned process repository through
  the same helper and prints its instruction digest, so a worker verifies
  an offer without handling a credential (#100).

### Claude Code members

- A Stop hook (`aicrew-agent wait-inbox`) wakes a member whose inbox
  changes. `GET /v1/crew/inbox/pending` lists unacknowledged messages
  without delivering them. Keep-alive and idle bounds are in `agent.json`
  `wake` (#95).
- `run` starts a Claude Code member on its first action, with no typed
  prompt; `--no-start` turns that first instruction off (#97).
- A member finds its role and its team's projects in its home:
  `session status` prints both, from `state/team.json`, which the launcher
  writes from `GET /v1/crew/projects` (#98).
- `join` writes managed `/crew-*` commands for every role (start, inbox,
  triage, offer, review, accept, submit, claim, handoff), rendered from
  ROLES.md's steps. It refuses and reports any that would shadow a
  built-in or the member's own command or skill. `run` starts with
  `/crew-start` (#99).
- `session start`, `session leave` and `run` are refused inside a launched
  client, whose launcher holds the session (#86).
- The guidance's safety rule forbids:
  - reading `creds/`;
  - putting a credential anywhere;
  - changing git's global or system configuration;
  - weakening TLS.

  A failed clone or fetch is stopped and reported. ROLES.md and the
  commands also name `inbox --ack` and `inbox --json` (#101).

### Operator console

- `aicrew hub-credential` replaces `introspection-credential`. Every secret
  `aicrew` writes takes `--output FILE|-` and never reaches a terminal.
  `--team-name` works wherever `--team` does. The docs write flags as
  `--name` (#87).

## [0.2.0] - 2026-10-03

The pilot's release. aicrewd is now the only process that opens the store:
the operator administers a running service through its operator API, with
`aicrew` as the console client, and each member's aimem installation lives
in its agent home, provisioned by `aicrew-agent join`.

### Breaking changes

- `aicrewd.json` requires `operator_token_file`: the owner-only file holding
  the operator credential. Create it with `aicrew operator-token new`;
  aicrewd refuses to start without it (#81).
- `aicrew` no longer opens the store: `-store` is removed. Every command
  reaches aicrewd over TLS with `-url`, `-tls-trust-mode`,
  `-tls-trust-value` and `-token-file`, or their `AICREW_*` environment
  variables (#82).
- A member's aimem installation is `<home>/aimem`. An agent home linked by
  0.1.0 takes the new layout and carriers on a `join` rerun; its
  installation is then provisioned with aimem's own commands under the
  home's variables (DEVELOPMENT.md), since `join` provisions only a new
  home (#76, #83).

### Operator API

- aicrewd serves team, invitation and introspection-credential
  administration under `/v1/admin/` on its HTTPS listener, authenticated by
  the operator credential, read from its file on every call so that
  replacing the file rotates it with no restart. A member's session token
  or aimem's introspection bearer is refused; failed authentications are
  limited per address, charged before the bearer is compared; every action
  is logged without a secret (#81).
- `aicrew` is the console client of that API, from any machine: credential
  bearers and invitation codes are still answered once and written only to
  a new owner-only file or a terminal, and an issue whose secret cannot be
  delivered is revoked (#82).

### Agent homes and aimem

- The member's aimem installation lives in its agent home: `join`, `check`
  and `run` give every aimem process the home's `AIMEM_STATE_DIR` and
  `AIMEM_SOCKET`, and the home's managed `.claude/settings.json` and
  `.mcp.json` carry them to clients started there by hand. `check` reports
  a carrier that disagrees with the home, foreign `AIMEM_*` values and
  user-scope aimem servers, and checks the credential in the home's
  installation (#76).
- `aicrew-agent join` provisions the home's installation itself, from the
  member's token file (or a hidden prompt) and the hub's CA, with the token
  only on aimem's standard input (#83).
- `aicrew-agent check` honors `CLAUDE_CONFIG_DIR` (#75); its tests ignore a
  developer's own (#77).

### Releases, tests and records

- The real-aimem end-to-end harness builds the aimem v0.7.4 release (#78).
- DEVELOPMENT.md explains why a dry run's sums differ from the release's
  (#79).
- The storage decision D-STORE is recorded in
  `docs/proposals/STORAGE-MODEL.md` (#80).

## [0.1.0] - 2026-10-02

The first release. aicrew runs a team of AI coding agents on top of aimem:
aimem owns the tasks, their reservations and the team's knowledge, and
aicrew owns the team, its members' sessions, the attempts and their
delivery. This release covers one team on one aimem hub, ready for the
first pilot: one coordinator, one worker, one project.

It ships three binaries: `aicrewd` (the service), `aicrew` (the operator's
command line) and `aicrew-agent` (each member's client).

### Teams, members and the operator's commands

- A store of agents, teams, their intended projects and memberships, with
  roles (coordinator, worker, independent), one store per database file
  and an audit of every change (#4, #13).
- The operator's command line: `aicrew team` creates, lists, shows,
  renames a team and sets its projects (#69); `aicrew invitation` issues,
  lists and revokes invitations (#53); `aicrew introspection-credential`
  issues, rotates and revokes aimem's credential (#24).

### Sessions, identity and team context

- Team sessions with generation fencing: a resume or an end fences the old
  generation everywhere, and ends its live coordination proofs (#5, #70).
- An agent is linked to its aimem identity through a proof aimem issues and
  aicrew redeems over identity.v1, and gets a session token on a fresh
  proof (#7, #25, #26).
- aimem checks a team session online through aicrew's introspection
  route, with its own credential and short-lived handles (#24).
- The client session API over RFC 8693 token exchange: entry, resume,
  handle refresh and leave, rate-limited (#23, #27, #28).

### Onboarding

- Single-use invitations for a team and role, redeemed with an identity
  proof, recovering from lost replies and concurrent completions (#8, #9,
  #12, #53).
- `aicrew-agent join` redeems an invitation at a hidden prompt and prepares
  the agent home: its layout, `agent.json` and managed guidance (#57, #60).
- `aicrew-agent check` verifies aimem, ai-skills and the client against a
  supported version set, and that the client sees aimem's MCP server and
  the required skills; it reports ready, restart required, or blocked with
  exact instructions (#59, #62). aimem v0.7.4, the first release with team
  sessions and `aimem hub credential`, is the tested release, installed
  through aimem's verifying installer (#74).

### Execution: attempts on aimem's reservations

- Attempts with one execution capacity per agent: a coordinator offers a
  task to a worker, who accepts or declines; an independent member claims
  a task for itself (#16, #17, #18, #21, #22).
- Work updates (block, resume, submit), result review, confirmed delivery
  and finalize; stop and release of a running attempt (#19, #20, #43, #44).
- Every transition that changes a task is a two-phase step: aicrewd records
  the intent, the member's client sends the reservation to aimem, and the
  step settles from aimem's read scope, so a lost reply never decides an
  outcome. A step that needs aimem to ask aicrew carries a coordination
  proof and settles by that proof's receipt; a work update (submit, block or
  resume) carries none and settles by its request key (#38, #39, #40, #41,
  #42, #44, #48, #51).
- Process pins on every attempt, with the instruction digest defined over
  the pinned manifest's exact bytes, and dependency evidence read before an
  offer (#39, #58, #72).
- aicrewd's reconciler settles the steps crashed members left, and closes
  attempts aimem recovered, through the read scope (#52, #54, #56).
- A work update advances the reservation's fence, as aimem does (#61).

### The member's client

- `aicrew-agent session` keeps a member's team session and aimem's binding
  of it, refreshing and resuming as needed (#29, #30, #31, #35).
- `aicrew-agent run` starts Claude Code or OpenCode inside the session and
  leaves when the client exits (#32, #33).
- `aicrew-agent step` drives each transition through the launcher over a
  private local socket, and recovers recorded steps after a crash (#45,
  #46, #49).
- The durable team inbox, and `aicrew-agent inbox`: lifecycle messages name
  their attempt, and an offer's message carries what the worker needs to
  start (#14, #15, #71, #72).
- The managed `docs/ROLES.md` in each agent home teaches every role's steps,
  the inbox rule and how to write for other readers (#72).

### Testing, releases and CI

- An end-to-end harness against a real aimem, with network, staleness,
  process, recovery and secrets faults, and a verified skip-the-fault
  matrix (#63, #65, #66).
- A tag-driven release workflow that publishes the three binaries for
  Linux, macOS and Windows with `SHA256SUMS` (#64).
- CI on Linux, macOS and Windows, with the race detector on the agent,
  server and store packages (#1, #50, #67, #68).

### Fixes

- Session routes' shared refusals use the documented envelope (#37); the
  tests observe an oversized body's refusal without a transport race (#36).
- Invalid UTF-8 is refused in stored text, and the input check no longer
  races the time package (#15, #68).

### Documents

- The agent workspace convention, the crew membership and execution
  contract, and the onboarding and identity-link contract (#2, #3, #6, #10,
  #11), with the review-gate rule for base-only updates (#55) and a
  proposal for an operator seat (#47).
